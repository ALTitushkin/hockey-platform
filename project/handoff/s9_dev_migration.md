## Задача одной строкой

Хоккей-бот уезжает с личного сервера (185.39.19.83, systemd) на app-VPS (88.218.250.212, Docker, юзер `deploy`), деплоится пушем в `main` через гейт тестов, и при падении шлёт алерт.

## Донор — PrizeDrawing, не с нуля

`Projects/PrizeDrawing/` уехал этим же маршрутом 11.07. Берём оттуда структуру и уже оплаченные болью решения:

- `Dockerfile` — python:3.12-slim, отдельный слой зависимостей, непривилегированный UID/GID 1000 (совпадает с логин-юзером Ubuntu, чтобы bind-mount писался без chown).
- `docker-compose.yml` — `env_file: .env`, `init: true` (tini как PID 1, корректный SIGTERM), `restart: unless-stopped`, `mem_limit`, `logging: json-file max-size 10m / max-file 3`.
- `deploy/deploy.sh` — `git pull --ff-only` → `docker compose up -d --build`.
- `.github/workflows/ci.yml` — job `gate` (ruff + pytest) и `deploy: needs: gate`, вызов `bash /opt/.../deploy.sh` (не напрямую — git на Windows не трекает exec-бит, SSH падал с 126).

Отличие от донора: хоккей-бот только long-polling. **Caddy, домен, TLS, webapp — не нужны.** Никакой SQLite тоже нет — бот стейтлесс, данные в git.

**Шаг 2 · CI.**
- **Job `test` уже написан и работает** — ruff → `validate_data.py` → `test_search.py` + `test_calendar.py`. Не переписывать, не «улучшать заодно». Трогаем только job `deploy`.

- **Флаг деплоя.** Как у донора: `vars.DEPLOY_ENABLED == 'true'`. Пока идёт переезд — `false`, чтобы CI не выкатил второй инстанс в момент, когда старый ещё жив.

**Шаг 3 · Перенос данных (до сноса старого).**
- Скопировать с личного сервера `/opt/hockey-platform/bot/queries.log` и `missing_queries.log` → в том на app-VPS.
- Сохранить копию `.env` локально у владельца (на случай, если токен рабочий и менять его не нужно).

**Шаг 4 · Переключение.** Строго в этом порядке:
1. На личном сервере: `sudo systemctl stop hockey-bot && sudo systemctl disable hockey-bot`.
2. Убедиться, что процесса нет: `ps aux | grep bot.py`.
3. На app-VPS: `docker compose up -d --build`.
4. Проверить в Telegram живыми командами: `/start`, поиск термина, `/today`, `/day 15.09`.
5. `DEPLOY_ENABLED=true`, тестовый пуш → деплой доехал, healthcheck зелёный.

**Шаг 5 · Алерт (P1).** Крон на app-VPS раз в 10 мин: контейнер не `running` **или** `getMe` не 200 → сообщение владельцу. Токен — отдельного служебного бота, не боевого. Проверить принудительным `docker stop hockey-bot`.

**Шаг 6 · Runbook.** `deploy/README.md`: как поднять с нуля на чистом сервере. Старый `deploy/hockey-bot.service` не удалять — пометить в шапке «архив, до 09.08.2026 (окно отката)».

## Грабли (не наступать заново)

- **`.env`:** строка `BOT_TOKEN=...` целиком, голый токен не парсится. **Без инлайн-комментариев** в строках значений — у донора это роняло прод.
- **PTB запинен `<22`.** 22.x ломает `run_polling`: процесс стартует и тихо выходит. Не обновлять «заодно».
- **Секреты в логах.** `logging.getLogger("httpx").setLevel(WARNING)` (и `httpcore`) уже стоит — при переезде не потерять. После первого старта **посмотреть `docker compose logs` глазами** на предмет токена, а не полагаться на код.
- **Два инстанса = 409 Conflict.** Единственная по-настоящему опасная ошибка этого спринта.
- **Коммиты.** Файлы готовит PM/дев, коммитит владелец на своей стороне: из песочницы `.git` на подключённом диске падает на `HEAD.lock`.
- **Не удалять старую установку** до 09.08 — это окно отката.

## Что делает владелец руками

1. Запускает `ops/hockey-bot-diag.cmd`, кладёт отчёт в чат.
2. Если токен отозван — новый через BotFather.
3. GitHub Secrets: `VPS_HOST` / `VPS_USER` / `VPS_SSH_KEY` → на app-VPS (`deploy@88.218.250.212`).
4. Создаёт служебного бота для алертов, кладёт его токен на сервер.
5. Repo Variables: `DEPLOY_ENABLED` — `false` на время переезда, `true` после проверки.
6. Приёмка в Telegram живыми командами.

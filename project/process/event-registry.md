# Реестр событий и публикаций

Кандидат v0.20.0,04.11.2026. Модули `news/event_registry.py`, `news/stories.py`, `news/publish.py`.

Проверки:199 unittest+26news+5delivery (230), Ruff. QA/security покрывают состояния,
доставку, восстановление, malformed данные и тождество канала. Промпт проверен на3
парных примерах (до/после): конкретная травма, нижняя часть тела и отсутствие диагноза.
После изменения подтверждённые уточнения сохранены, неизвестные не выдуманы. Выборка
маленькая, статистической гарантией качества любых текстов не является.

## Что сравнивается

Совпадение NHL ID игрока связывает материалы, но само по себе никогда не подавляет
новость. Убраны старые эвристики same_event по общему игроку и report_heads по фамилии.
До чтения источника тождество доказывает только ID самого документа.

Детерминированный разбор выделяет family, actors, clubs, effective_date, phase, facts.
Для подписаний различаются PTO, стандартный/entry-level контракт и прекращение;
в фактах — срок и денежные значения. Для здоровья — уход, отсутствие, тренировка,
активация, возвращение и операция; уточнения — регион, диагноз, срок/статус отсутствия.
Денежные записи нормализуются, диапазоны сроков сохраняются.

Для автоматического тождества нужны один участник, один клуб, установленное действие,
его дата и достаточные поддержанные факты. Дата статьи не подменяет дату события.
Дата связывается с глаголом действия, а не произвольной датой биографии или тренировки.
Изменившиеся фазa, срок или диагноз дают другую версию. Новые факты за пределами
вводного абзаца, которые нельзя уверенно связать с героем, переводят материал на review.
Прогноз возвращения не выдаётся за состоявшееся возвращение.

Точная версия — SHA256 канонического набора полей. Текст статьи/URL не является
идентичностью события. Подтверждённая опубликованная версия повторно не генерируется.
Новая версия не запрещена из-за того же игрока. Неполный разбор сохраняется в черновике
с объяснением; его нельзя молча отбросить как дубль.

Это поддержанные схемы, не универсальный NLP-анализ произвольной новости. Несколько
участников/клубов, неустановленная дата, непривязанные условия и неизвестные действия
требуют редакторской проверки. Две разные травмы не объединяются только из-за ссылки
на старую статью: backlink устанавливает связь материалов, не дату или тождество.

## Постоянное хранение

SQLite `news/out/event_registry.sqlite3` на существующем runtime-томе:

- documents — источник и извлечённые факты, в том числе неполные;
- revisions — канонические полные версии и индекс тем;
- publications — уникальная пара версия/постоянный канал, документ, исход, ID сообщений;
- archive_files — индекс уже прочитанного архива по mtime/size;
- resolutions — журнал явных операторских сверок неопределённой отправки.

Архив индексируется инкрементально. Замороженная `event_receipts` подтверждает именно
отправленную версию. Меняемое `data.event_revision` плюс старые published/messages не
создают подтверждение новой публикации. Пересборка сохраняет квитанцию, отказ и удаление.
Старый архив без структурированных квитанций сохраняется как источник связи, но не
превращается в уверенно восстановленные факты автоматически. Backlinks таких материалов
дают review, а не запрет всех новостей игрока.

## Защита отправки

Перед сетью SQLite атомарно резервирует `(revision, channel)`. Telegram username
разрешается через getChat в постоянный числовой ID один раз на процесс; этот же ID
используется для отправки и ключа реестра. Публичный username в JSON сохранён для ссылок.
Неподтверждённый ID останавливает отправку с диагностикой.

Успех записывается в SQLite до обновления JSON. Если запись JSON прервана, повтор
восстанавливает ID сообщений без повторной отправки. Другая статья с той же версией
блокируется также при ручной кнопке. Учитываются разные каналы доставки.

Сбой после начала сетевой операции имеет неоднозначный исход: автоматического
истечения блокировки нет. Оператор сначала сверяет канал. Затем вызывает
`Registry.resolve(event, channel, sent=True, messages=[...], note="...")` при найденной
публикации либо `sent=False, messages=[]` после подтверждения отсутствия сообщения.
Сверка фиксируется в журнале; только verified_not_sent разрешает новую попытку.
Это предотвращение повторов, а не обещание exactly-once для неидемпотентного Telegram API.

## Выкладка и откат

Первое обращение создаёт таблицы SQLite; существующие черновики/overlay не заменяются.
Откат на образ v0.19.0 не требует удаления БД: старый код её игнорирует. После отката
новые гарантии дедупа временно не работают; файл и квитанции нужно сохранить.
Автоматическая генерация не добавляет модельных запросов для реестра; матчевые вводные
вообще больше не обращаются к модели.

CI проверяет отсутствие конфликта версии до деплоя, фиксирует серверный checkout на
тот же SHA, что и news image, и проверяет его в deploy.sh без повторного pull main.
После успешного deploy аннотированный тег создаёт отдельный job с contents:write;
ручной rollback dispatch тега не создаёт. Теги не перезаписываются. Checkout прекращается
при неизвестных изменениях отслеживаемых серверных файлов; reset/clean не используются.

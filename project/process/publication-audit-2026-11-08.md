# Диагностика публикаций 08.11.2026

Свежая проверка SSH: логи news за36ч, скачаны14 сегодняшних JSON и одна PNG
в игнорируемую news/out/audit-2026-11-08/. Сервер, состояния, публикации не менялись.
Проверена именно редакторская карточка a89d4c96, публичная лента не осматривалась.

## Подтверждённые причины

- Регулярные league/night сегодня опубликованы: канал message_id69/70, подтверждены
  логами автопубликации. Инфоповоды доставляются в личку, их лог «ок» не означает канал.
- Сегодня12 story-черновиков:9 версий Status Report07.11 и3 Ньюджент-Хопкинса.
  Все с event_decision=review. Свободный пересказ дополнительно всегда получает
  примечание о необходимости редакторского подтверждения в stories.py.
- editorial_lifecycle.classify для story без expires_at допускает ready только
  для complete signing; остальные получают needs_revalidation. В частности свежие
  injury_minor без срока не могут публиковаться даже вручную. publish.review показывает
  «Опубликовать» только для ready; исправления/перепроверки интерфейс пока не предлагает.
  Это незавершённый жизненный цикл после v0.21.1, а не ошибка Telegram или выключенное авто.
- Реальная PNG a89d4c96 показывает Ванкувер рядом с Райаном Ньюджент-Хопкинсом.
  source_event.teams=[EDM]. stories.card сначала ищет в пересказе клубы из всего
  источника; упомянутый соперник VAN вытесняет тег EDM. Общая причина допускает
  повторение на других травмах. Требуется доказанная привязка клуба к герою карточки.
- source_watch создаёт новый document ID при изменении всего текста/тегов/contentDate.
  Изменения источника действительно есть: например в одной версии травмы добавлен
  итог4:2 и изменено представление клуба. Есть и повтор одного source content_hash
  у разных черновиков Status Report (4752d757/781a1e91). Это свидетельство повторного
  создания версии, требует отдельной проверки идентичности в watch/feed и дедупа review.
  Нельзя объявлять все12 материалов новыми событиями или все изменения чисто техническими.

## Следующий шаг

Исправить выбор клуба и добавить регрессию на сохранённом случае EDM/VAN; реализовать
свежую проверку/исправление версии через очередь, затем объединение обновлений одного
документа без повторного уведомления при прежних фактах. Не открывать публикацию
одним снятием needs_revalidation: дата/доказательства и качество пересказа ещё требуют проверки.
В этой диагностике код не менялся, тесты/LLM не запускались, релиз не выполнялся.

## Проверка регрессии и подхода к изменениям

По вопросу владельца08.11 проверены git diff a9499a6 и отчёты v0.21.0/v0.21.1.
Подтверждено изменение рабочего поведения: v0.21.1 включил lifecycle.classify в общий
decision до ручного допуска; свежие injury без срока теперь запрещены и вручную.
До этого manual decision не требовал такой классификации. Отчёт релиза прямо оставлял
получение свежего источника и исправление из Telegram на следующий пакет. Таким образом,
усиление запрета и доступный путь восстановления выпущены несогласованно.
Это подтверждённая регрессия доступности сценария; она не означает, что прежние тексты
были фактически корректны и их безопасно разрешить без проверки.

Оба отчёта честно ограничивали проверку runtime smoke и не подтверждали полный новый
цикл публикации. Тем не менее этого оказалось недостаточно как критерия готовности:
270/286 проверок и работающий контейнер не выявили непроходимый полезный сценарий.
Единая целевая архитектура есть, но реализация пока гибридная. Рекомендация: до новых
возможностей выполнить стабилизацию существующего пути; для каждого изменения показать
до/после на фиксированном корпусе, сохранение корректных успешных сценариев и исправление
ошибочных. Начать с малого вертикального пути одной injury (источник→факты→текст/карточка→
проверка→auto или разрешимое review), не с внедрения всего архитектурного плана сразу.
Полный откат не выбран: он может вернуть старые ошибки смысла/устаревшие материалы.
